Case studies

1 · Inbound lead concierge: form → CRM → drafted reply → one-tap approval

TypeScript · HubSpot API · Telegram · Resend · webhook API

A form submission becomes a CRM record and an LLM-drafted reply, which arrive on my phone as an approval card. One tap sends it, and delivery and open events are written back to the deal. Two systems can write the reply, and redundancy alone means the faster one always wins. So a cached health verdict decides precedence, with a 5-minute grace period and a 20-minute safety net. The approval card is the product: a human stays on the last click of anything that reaches a customer.

2 · Job-discovery engine: LangGraph, LLM judge, human interrupt, outcome feedback

Python · LangGraph · SQLite checkpointing · pytest
  • State machine: gate → score → route → notify, checkpointed so a crash resumes instead of restarting.
  • An LLM judge scores fit, and a trust clamp limits how far keyword rules can overrule it. That clamp fixed an incident where keyword bonuses were silently outvoting a correct "no".
  • A feedback loop reads what I actually did in the CRM, including my typed reasons, and writes it back into the judge's prompt. It fails closed when the LLM is down: no score is better than a made-up one.
  • It originally auto-applied. I measured the result, volume and zero outcomes, and removed that feature.

3 · Correctness of agent output: the part I treat as the real job

Harness · context management · self-correction
  • Grounded generation: the daily article generator collects production evidence first (commits, uptimes, CRM counts). A gate rejects any figure it cannot trace, then retries up to 4 times with a different angle, and salvages sourced paragraphs instead of discarding the draft.
  • Context across agents: two coding agents work the same repo without seeing each other's chats. A shared file acts as their working memory: a claim board before touching files, a handoff block (done / next / verified by / risk), and a start-of-session check that the last change produced output, not just that it ran.
  • Read-back verification. This week an audit that reads the CRM back showed a pipeline reporting success while only 11 of 23 job records had a real cover letter. A refused API call was being logged as "no data". I added retry-on-429, made failed lookups raise, added a self-healing job every 2 hours and a daily audit with alerts. Result: 19 of 23 complete, and the remaining 4 proven to be closed postings.

4 · Five-provider LLM chain, ordered per use case

Claude · OpenAI · Gemini · Groq · Grok

One API key is a single point of failure for the whole operation. On 19 Aug 2026 my primary provider's balance hit zero, and the chain fell through to the next provider in 2.4 seconds with no lost request. The lesson that took longer: the order must differ by use case. Reasoning models can return empty strings under low token budgets, so a classification chain that leads with one fails silently. Client-facing copy leads with the strongest model; classification leads with the cheapest one that clears the bar.

Principles I would bring to Ripio's internal tooling

Measure at the edge, not the sourceA commit is not a deploy, and an accepted email is not a delivered one. Verify where the request actually lands.
Unmeasured is not zeroA tracker exits non-zero when it cannot measure, so "nothing counted" never looks like "nothing happened".
Fail open or closed, per systemAlerting fails open: a duplicate beats silence. Publishing and money fail closed.
Every record names its authorMany agents write to one CRM, and a source prefix turns provenance into a filter.
Write the failure downA public incident record: 22 incidents and 19 named failure modes, each with the measured number that proves it.
